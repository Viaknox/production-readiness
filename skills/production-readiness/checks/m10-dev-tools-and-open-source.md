# M10 · Dev tools & open source

**Scope.** What makes a developer tool, library, plugin, or open-source project trustworthy to install, depend on, and contribute to.

**Switched on when.** The product is a developer tool, library, plugin, or open-source project distributed to other developers.

**Scoring.** Every item is PASS, GAP, N/A or UNKNOWN. PASS needs evidence — a file path, config, CI run, dashboard or doc link. A README claim is not evidence.

| # | Check | Required at | Evidence that satisfies | Common gap in AI-built products |
|---|---|---|---|---|
| 10.1 | License chosen deliberately (copyleft like AGPL can block company adoption; permissive like MIT/Apache spreads faster) and NOTICE/third-party licenses correct | T1 | LICENSE file + NOTICE/third-party license file, with a note on why that license was chosen | A license auto-generated by the scaffold tool with no thought to adoption impact, and no NOTICE file for bundled dependencies |
| 10.2 | `SECURITY.md` with a private disclosure channel | T1 | `SECURITY.md` file present with a working private contact (email/security.txt) | No `SECURITY.md`, so a researcher has no private channel and defaults to a public issue |
| 10.3 | Semantic versioning, CHANGELOG, and a tested upgrade/migration path for any stored data or config format | T2 | CHANGELOG with semver-tagged releases + a tested migration script/guide for a stored format change | Versions bumped inconsistently, and a config/schema change breaks existing installs with no migration path |
| 10.4 | Supported-platform matrix actually tested in CI (OS × runtime versions × each client/IDE it claims to support) | T2 | CI config showing a matrix build across the claimed OS/runtime/client combinations, with a passing run | README claims support for platforms that have never actually run in CI |
| 10.5 | Install verified from a clean machine for every documented path | T1 | A dated log/recording of a clean-machine install following each documented install path | Install instructions only ever tested on the maintainer's already-configured machine |
| 10.6 | Package names reserved on each registry (PyPI, npm, plugin marketplaces) | T1 | Registry page showing the package name registered under the project's account | Package name still available for squatting because it was never reserved before announcing |
| 10.7 | Signed releases / build provenance | T2 | Release signing config (e.g., Sigstore, GPG) or provenance attestation attached to a release | Releases published with no signature, so tampering can't be detected |
| 10.8 | Telemetry off or opt-in and documented | T1 | Telemetry config showing default-off or opt-in behavior, documented in the README/docs | Telemetry collected by default with no disclosure in the docs |
| 10.9 | CONTRIBUTING, code of conduct, issue/PR templates | T2 | `CONTRIBUTING.md`, code of conduct file, and issue/PR templates present in the repo | Repo accepts contributions with no guidance, producing inconsistent PRs and no conduct policy |
| 10.10 | A "what this is not" section so users don't misuse it | T2 | README/docs section explicitly scoping out unsupported use cases | Users adopt the tool for a use case it was never built or tested for, then file bugs against it |

**Right-sizing notes.**
- License clarity (10.1), a private disclosure channel (10.2), a real clean-install test (10.5), reserved package names (10.6), and opt-in telemetry (10.8) are T1 because they affect trust and legal exposure from the first public release.
- CI platform-matrix testing (10.4), signed releases (10.7), and community-process files (10.9, 10.10) are T2 — expected once the project has external users and contributors, not necessarily at a first tagged release.
- A single-maintainer, pre-1.0 project can mark 10.4 and 10.9 as GAP-but-LATER rather than BLOCKER if it's honest about that status in the README.
